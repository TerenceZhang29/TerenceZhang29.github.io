~/projects/amazon/source

Amazon · 2023–2025 · design author & lead engineer

Source: a deterministic lineage layer under 44 billion original images.

The data and ingestion architecture that stores, sanitizes and indexes every original upload at full fidelity, with two-way lineage to every variant made from it. It replaced eventually consistent index queries with deterministic key lookups inside a live upload pipeline.

  • Distributed Systems
  • Data Modeling
  • Concurrency
  • Storage Architecture

01 / architecture

How it works

  • New
  • Changed
  • Unchanged
  • Removed from the lookup path
  1. 1Deterministic compound keyRecords are keyed on a 160-bit SHA-1 hash plus file type, in one strongly consistent lookup before any processing. Adding the file type resolves zero-byte and cross-format collisions.
  2. 2Sanitize once, inherit everywhereGPS and other sensitive EXIF data are scrubbed at upload. Fixed attributes (aspect ratio, moderation flags, AI-generation markers) are extracted once and inherited by every variant, with no repeated compute.
  3. 3Atomic distributed lockA conditional write acts as a per-record lock, so parallel uploads of the same file produce exactly one record and one stored object, with no race conditions.
  4. 4Prefix-partitioned storageThe first 4 hex characters of the hash spread files over 65,536 prefixes. This resolved the staging bottleneck behind ~800,000 failed requests in 90 days.
  5. 5Bidirectional lineageNested source-to-variant maps plus a transformation history let you trace both ways, from an original to every thumbnail, localized graphic and compressed web format, and back.
  6. 6Backfill billions of originalsEvery existing original is converted into a record, and duplicate copies left by older bugs are merged along the way.

03 / decisions

Key decisions

  • SHA-1 fingerprints instead of MD5 or SHA-256MD5 reaches a 50% collision chance at around 5 billion records, well below this catalog's size. SHA-1 pushes that past 1024 while running only about 20% slower than MD5. SHA-256 cost about 60% more, and its extra attack resistance doesn't matter for deduplication. The old MD5 value is kept so existing customers don't break.
  • A new record type, not a reused oneStoring originals in the existing copies table would have been less work up front. It would also have grown that table by 30%+ and kept the slow index in the critical path. A separate table keyed by fingerprint and file type removes the index from lookups entirely.
  • Phase 2: customer-defined groups, not hard-coded linksFor teams that make derived images, such as one product photo localized into many languages, I designed "source groups" where each team defines its own relationship schema. I rejected a simpler option that would have locked every group to one parent image, because that choice would be hard to reverse later.

~/projects/amazon/one-click-takedown

Amazon · 2022–2023 · design & build

One-click take-down: cascading removal across every copy, cache and collection.

A state-driven deletion engine that removes a compromised, copyrighted or legally sensitive image and everything derived from it, from database records to edge caches, then blocks it from being uploaded again.

01 / architecture

How it works

  • New
  • Changed
  • Unchanged
  • Failure path
  1. 1Block before deleteThe file's checksum is blocklisted first, so banned media can't be uploaded again while the teardown runs, or after it finishes.
  2. 2Cross-tenant discoveryEvery reference to the image is found across customer collections and snapshotted to storage before anything is deleted, for audit and resumability.
  3. 3Volume-aware branchingNo links: skip ahead. A few: remove them inline with a resumable index. Many: fan out to parallel batch deletion jobs.
  4. 4Bounded tracking, dead-letter logA tracker polls batch jobs up to 20 times and reports what failed. Every failed deletion lands in a dead-letter bucket for audit and replay.
  5. 5Cascade to every derivativeRelated variants are found and destroyed, the workflow confirms they're all gone, and only then removes the stored originals. Translated copies are purged automatically too.
  6. 6Edge to storage, rolled out safelyThe run ends with CDN invalidation. Because it handles live traffic, the new workflow was dialled up gradually, with a metric and an alarm for every failure scenario.

Trade-offs, measured

Seconds, log scale

The files couldn't be fetched through any existing API, so they had to be found in the data warehouse. Each was then checked against the live system before deletion. The purge ran as a tracked change with monitoring throughout.

~/projects/amazon/perceptual-compression

Amazon · 2024–2025 · design author & lead engineer

Perceptual compression engine: the smallest file that still looks right.

An automated optimization pipeline for marketing and storefront graphics. Each image is compressed 60 ways in parallel and scored for how it looks to a human, and the smallest file that clears a quality floor ships.

01 / architecture

How it works

  • New
  • Changed
  • Existing
  1. 1Parallel enumeration30 quality levels (99 down to 70) × chroma subsampling on and off gives 60 compressions per image, all run at once. The whole space is searched in one round-trip of about 10 s.
  2. 2Perceptual scoring at scaleThe SSIMULACRA 2 binary is packaged into the serverless runtime. Each worker downloads the original and its candidate, scores them, and returns size and score.
  3. 3Selection ruleBy default, the smallest file scoring at least 80 wins. The chosen level and score go back in the response, so marketers see the quality cost of every file.
  4. 4Bounded binary searchFor the ~5% of requests with a hard file-size cap, a search from Q0 up to the default level runs at most 3 iterations and stops once the range is 5 levels or fewer. This caps latency and rendering cost.
  5. 5Async lineageAfter the response, a background job records the original as a source and each output as a variant, using Source. Lineage adds no latency, and repeat requests can reuse results.
  6. 6Backward-compatible APIA new quality mode and max-file-size field on the existing optimize API. Marketing tools preview the default result through a 30-day temporary URL and set a size cap only when they need one.
